# I1 JSON request / response contract

### Request (stdin)

`operation`: **required** string `cdmcs_schedule_v1`.

- `horizon_minutes`: integer `H` in `[1,100800]`, **UTC elapsed minutes** from a caller-chosen UTC anchor.
- `duration`: positive requested-meeting duration in minutes.
- `candidate_starts`: nonempty, unique integer starting times, each satisfying `0 ≤ t ≤ H-duration`.
- `replacement_starts`: unique integer starting times for an existing flexible meeting (the moved meeting's own duration may rule out individual starts).
- `required_people`: nonempty, unique participant ID strings; `required_resources`: unique exclusive resource IDs.
- `existing`: array of `{id,start,duration,people,resources,flexible}`. `id` must be unique and not `NEW`. The baseline calendar **must be conflict-free for every required person/resource**. Only meetings marked `flexible:true` can be proposed for relocation. Adjacent half-open intervals are legal.
- `profiles`: object keyed by *every* person appearing in the requested meeting or existing meetings. Each value contains `rate_prefix` (H+1 cumulative nondecreasing nonnegative integers, beginning at zero), `published` and `exceptions` arrays of `[start,end]` intervals, `preferred_break`, `gap_weight`, `nearby_limit`, and `exception_fee`.
- `local_day_index`: H+1 ordered integer local date ordinals, generated by the caller's timezone-aware preprocessing. They need not start at zero; their order must be nondecreasing.
- `unresolved_people`: optional array of user IDs with unknown calendar provenance, always treated as blocking rather than assumed free.
- `move_fixed_cost`, `move_participant_cost`, `delay_per_day`: optional nonnegative illustrative cost parameters.
- `limit`: optional integer 1–100, default 5.

The program reads **one JSON document from stdin**, performs no file or database
I/O, and exits with code 0 for a valid completed evaluation (including no feasible
proposal or unresolved calendars). Input/implementation-budget rejection returns
`{"status":"INVALID_INPUT","error":"..."}` and exit code 2. Unexpected engine
failure or allocation failure returns `{"status":"ENGINE_ERROR","error":"..."}`
and exit code 3. No partial recommendations are returned on failure. Catching
allocation failure is best effort; an OS kill or broken output pipe cannot be
guaranteed to produce JSON. A future caller must enforce a process timeout and
check both exit status and JSON.

### Response (stdout)

`status` is `OK`, `NO_FEASIBLE_PROPOSAL`, `UNRESOLVED_CALENDAR`, `INVALID_INPUT`,
or `ENGINE_ERROR`.

A successful case includes `solutions_evaluated`, `returned_count`, `truncated` and `recommendations` sorted by `(total_cost,fairness_max_burden,start_minute,moved_meeting_id,replacement_start_minute)`.

Each recommendation includes:

- `start_minute`, `end_minute` — proposed new meeting time.
- `total_cost` and `fairness_max_burden` — signed integer total cost and nonnegative burden max.
- `moved_meeting_id`, `replacement_start_minute` — nullable when no relocation.
- `required_permissions.new_meeting_extra_availability`, `.relocated_meeting_extra_availability`, `.relocation_participant_approval` — lists of affected IDs; actual consent is **not** obtained by the CLI.
- `proposal_status`: `DIRECT_PENDING_NORMAL_MEETING_APPROVAL` or `CONDITIONAL_PENDING_APPROVAL`.

### Availability and cost semantics

An event is available for a participant when the event fits fully inside at least one published window, or else fits fully inside an explicit exception window and is flagged for permission. An exception cannot override a protected recorded commitment. No room-availability policy is invented; rooms/resources are protected through supplied calendar commitments.

Personal preference cost is the change in:

`sum(event prefix-rate costs) + sum(gap costs for adjacent nearby meetings starting on the same local civil date)`.

A gap penalty is `abs(actual_gap - preferred_break) * gap_weight` when the gap is ≤ `nearby_limit`; otherwise 0. We add per-event extra-availability exception fees, per-affected-participant relocation fees, a fixed relocation fee, and a calendar-date delay cost. Cost weights are **synthetic** until calibrated.

Fairness is maximum of `max(0, per-person net inconvenience)` across affected participants; the fixed administrative move penalty and delay are in total cost but not attributed to individual fairness, matching V15.

### Implementation bounds (I2)

These limits reject a computation, not the mathematical existence of a schedule.

| Quantity | Limit |
|---|---:|
| UTF-8 stdin bytes, including whitespace | 16 MiB before DOM parsing |
| JSON nesting | 32 (Boost.JSON default) |
| Horizon | 1-100800 UTC minutes |
| Candidate / replacement starts | 10000 each, distinct |
| Candidate count times max(1, replacement count) | 2000000 |
| Existing meetings | 10000, conflict-free on every typed key |
| ID string length | 256 UTF-8 bytes |
| Members per person/resource/unknown-ID list | 256 |
| Total existing person/resource memberships | 100000 |
| Profiles / total prefix entries | 256 / 3000000 |
| Windows per published or exception list | 1024 |
| Cached replacement records plus copied memberships/exception IDs | 250000 |
| Logical search work units | 10000000 |
| Output limit | 1-100 |

The search budget counts availability-window visits, participant visits, index
key/overlap visits, candidate visits, joint key-comparison bounds and conservative
per-score person-work units. It is a deterministic safety budget, not a wall-clock
guarantee. The entire invocation fails if exhausted, even if some proposals have
already been evaluated internally.

Prefixes begin at zero, are nondecreasing, at most 10^12, with increments at most
10^8. Fixed/participant/delay costs are 0-10^7. Preferred breaks are 0-1440,
gap weights 0-100000, nearby limits 0-10080, exception fees 0-10^7.
Day ordinals are signed 32-bit, nondecreasing; differences are computed in 64-bit.
The engine cannot verify that these arrays represent a truthful timezone calendar.
Historical timezone transitions that make local dates decrease are outside this
contract and rejected; the tested Istanbul and Berlin mappings do not do so.

Unknown object fields are ignored. Duplicate object member names follow the
underlying JSON parser's last-member-wins behavior; generate unique keys.
Invalid UTF-8, noninteger numeric fields, booleans used as numbers, malformed JSON,
multiple JSON documents and invalid relationships are rejected. There is no
`runId`, `engineVersion` or application `protocolVersion` envelope yet: the version
is the operation name. This is NOT the production appointment JSON contract.

`UNRESOLVED_CALENDAR` includes zero counts, `truncated:false`, and an empty
recommendation list. `solutions_evaluated` counts feasible arrangements (including
different moves for one start), not the number of candidate starts examined.
