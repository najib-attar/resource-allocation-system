# Private personal scheduling preferences (D3-B)

This is an internal persistence foundation, not a scheduling feature activation.
There are no routes, UI, cost policies, preference compilation, calendar reads,
engine calls, booking changes or new scheduling initiation permissions.

## Ownership and schema

Migration `0050a`, after `0049b`, adds one empty table,
`scheduling_preference_revision`. Its composite key is `(owner_id, revision)`.
`owner_id` references `university_user.id` with RESTRICT, not `login_account`:
university identity owns the history independently of a provisioned login.
No user, role, faculty, settings-head or separate audit table is duplicated.

| Column | Type and meaning |
|---|---|
| owner_id | INTEGER, university identity FK and first PK column |
| revision | Positive BIGINT, second PK column; never an identity sequence |
| contract_version | Positive INTEGER; current writer supports 1 only |
| status | `configured` or `deactivated` |
| timezone | Nullable VARCHAR(256), bounded to 256 UTF-8 bytes |
| effective_from / effective_until | Nullable local DATEs, inclusive, 1970 through 2099 |
| preferred_weekdays | Nullable JSONB array, at most seven ISO weekdays |
| preferred_windows | Nullable JSONB array, at most 64 original windows and 16 KiB |
| gap_indifferent | Nullable BOOLEAN; explicit indifference is not zero minutes |
| desired_gap_minutes | Nullable INTEGER, 0 through 1440 |
| created_at | NOT NULL TIMESTAMPTZ generated by PostgreSQL `clock_timestamp()` |

Configured revisions require every intent value; indifferent gaps have NULL
minutes, while a specified gap must have minutes. Deactivated revisions contain
NULL intent fields. Database checks enforce the row shape, dates and JSON bounds;
the shared application validator also checks exact fields, types, IANA identifiers,
duplicate weekdays, source clocks, overlaps and weekday/window consistency.
The PK index supports owner-scoped descending latest/history queries without a
separate current pointer. The owner is also the actor: delegated edits do not exist.

## Shared values, separate trust

`web/preference_values.py` contains pure, immutable intent validation and a bounded
UTF-8 JSON reader (4 MiB, depth 32, no duplicate keys or nonfinite numbers).
D1 reuses these values but keeps its synthetic/version/provenance envelope.
Its unchanged tests must pass; value parsing alone authorizes neither execution
nor export. Production input is exactly `preference_version` plus `timezone`,
`effective`, `preferred_weekdays`, `preferred_windows`, `desired_gap_minutes`.
Owner, revision, state, synthetic markers and provenance are not accepted in it.

Original windows are retained, including `24:00` end clocks, Sunday wrapping and
overnight endpoints. Normalized segments are only validation artifacts; persisting
them alone would lose the DST endpoints required by D1. Touching windows may merge
for validation but both supplied endpoints survive storage. Empty arrays and
`indifferent` are explicit choices; omitted or NULL values are rejected.

Storage validates IANA/clock/date structure without expanding dated calendars.
A weekly wall-time preference is not an appointment instant. Ambiguous/nonexistent
dated endpoints must still be rejected by a future bounded compiler, as in D1;
storing a valid foreign timezone does not enable mixed-timezone compilation.
Effective dates must cover any future full cost context, including relevant
neighbors outside the search horizon. Neither numeric weights nor neutral costs
are invented. Desired breaks remain soft preferences, never published availability.

## Internal service and authorization

`SchedulingPreferenceService` has no owner/actor argument:

- `current()` returns the newest own revision, or missing/revision zero.
- `history(limit=20, before_revision=None)` returns at most 100 own private views,
  newest first; the exclusive revision cursor never switches owners.
- `replace(expected_revision, document)` appends a complete configured revision.
- `deactivate(expected_revision)` appends a deactivated revision, not erasure.

Every method requires a server-authenticated Flask request context, matching signed
session identity/version, `Principal`, authenticated database URL and session bind.
Identity is refreshed using `AccountService.identity(..., session=...)` in the same
clean transaction. Forged/stale principals, revoked sessions, disabled or missing
accounts and inactive university users are denied. All existing roles have identical
self-only rights. Administration grants no cross-user access or editing override.

Reads use PostgreSQL REPEATABLE READ, READ ONLY, with autoflush suppressed. Writes
lock the login account FOR UPDATE and university identity FOR SHARE before current
identity/revision checks. Revocation, deletion, inactivation and competing self-writes
therefore serialize with writes. Reads are coherent as of their transaction snapshot;
revocation cannot retract information already read before it committed.

The expected revision must equal the latest persisted revision. A successful append
uses exactly current+1; BIGINT exhaustion and stale submissions conflict. A unique
PK is the final conflict guard. Transaction ownership stays with `Database.transaction`;
helpers do not independently commit. Failed validation, authorization, flush or
commit never publishes a successful write or partial history.

Latest means newest **before** state/date checks. A future-dated replacement
immediately supersedes the old profile. Deactivation, unsupported versions and
unreadable data never search backward for an older configured profile.

| Runtime result | Meaning |
|---|---|
| missing, revision 0 | No saved revision |
| missing, deactivated status | Explicit newest deactivation; older history retained |
| configured | Valid explicit stored intent, not blanket compilation eligibility |
| unsupported | Unsupported stored contract version or unavailable timezone |
| unknown | Unreadable values; database failures raise sanitized storage errors |

Private DTOs/reprs withhold contents unless the authenticated owner explicitly
requests `document()`. Returned documents carry `origin=personal_preference`, not
synthetic provenance. No existing administration, raw-data, calendar or research
view is extended. Database exceptions are replaced without SQL, parameters,
credentials or chained private dependency messages. Production logging must not
enable SQL payload logging. This is a trusted backend boundary, not protection
against malicious Python code or database owners.

## Retention, account lifecycle and authorized erasure

UPDATE, DELETE and TRUNCATE are rejected by migration-owned history triggers.
Account disable/revocation/deletion does not erase preferences. A deleted login
cannot access history; the university identity remains the owner. Permanent user
deletion is restricted while preference history exists.

No retention duration, user-facing erasure or new privileged role is invented.
An institution-approved DBA process can erase a specified owner's records in an
audited transaction. First disable the account, revoke its sessions and drain
in-flight preference operations; otherwise erasure could race a new append or
reuse an old optimistic revision. Then explicitly disable the row history trigger,
delete only the approved owner's rows, and re-enable it. That operation requires table-owner
or equivalent privileges and must not be available to the ordinary application
role. Transactional rollback restores both records and trigger state. This guarded
DDL capability is deliberately not removed or exposed through an application API.
Future deployment needs an approved retention/audit/backup-erasure procedure and
appropriate separation of migration/DBA and non-owner application credentials.

Account deletion/recreation is not password reset. Existing provisioning starts a
new login row at session version 1. A synthetic D3-B.5 witness confirmed that a
previously revoked session can read its preferences again after manual login
deletion and reprovisioning with that reused generation. This requires a separate
privileged account deletion, not a preference operation; there is no preference
route or account-deletion workflow added here. D3-B does not change global authentication.
Do not use that unsupported recovery procedure: existing password reset/revoke
preserves the account and advances its version. A recreated account must use a
non-reused generation or invalidate prior cookies through separately reviewed
account-lifecycle hardening before production use of such recovery. Tests cover
deleted-account denial and recovery with an explicitly new session version.

Empty-table downgrade is reversible. Downgrade takes an ACCESS EXCLUSIVE table
lock before checking for history, preventing a concurrent append from committing
between the empty check and DROP. Without that lock a two-transaction regression
reproduced silent loss of a newly appended revision; the corrected test verifies
the append cannot commit through that gap. Populated history blocks downgrade
pending explicit authorized retention/erasure review.
All migrations and erasure tests run only in disposable synthetic databases.

Minimum deployment separation: migrations/authorized erasure use a distinct owner
role. Ordinary application credentials must be non-owner, non-superuser, unable to
assume that owner role, and unable to disable triggers or perform DDL. Grant only
the required SELECT/INSERT access on preference history, not UPDATE/DELETE/TRUNCATE;
end users receive no direct SQL access. These are deployment requirements, not new
roles or grants installed by this migration. Database/server payload logging,
backup retention and erasure auditing require a separately approved operational
policy; sanitized service exceptions do not sanitize privileged database logs.

Database checks enforce state shape, types and bounds, not a second implementation
of weekly-window validation. Direct SQL can insert semantically invalid window
arrays or duplicate weekdays; every read revalidates them and returns unknown
without values or fallback. This is not a public SQL interface or an authorization
grant. Valid timezone storage likewise does not imply compiler compatibility.

## Verification boundaries

The tests cover all existing roles, forged identities/owners, wrong databases and
session binds, revocation/inactivation, concurrent first creation and update/clear,
consistent reads, immutable history, bounded paging, JSON/numeric/timezone limits,
overnight source preservation, rollback, empty/populated downgrade and DBA erasure.
They also require no engine calls/calendar queries and no changes to other tables.
Local D3-B.5 verification used Windows, Python 3.12.14 and isolated PostgreSQL 17.11:

| Suite | Executed result |
|---|---|
| Full application Python/PostgreSQL | 552 run: 551 passed, one POSIX execute-permission test skipped on Windows |
| Shared values / preference persistence | 11 / 40 passed, combined zero-skip gate 51; also included in the full run |
| D1 / D2 | 84 / 56 passed, zero skips |
| I3a / I3b plus identity / I3c | 37 / 55 / 47 passed, zero skips |
| Application C++ | 192 passed, plus two standalone CSV smoke checks |
| Standalone CDMCS | 618 differential cases and 25 safety methods passed |
| Migration / metadata | Fresh upgrade, locked concurrent downgrade, empty downgrade/re-upgrade, populated refusal and no drift verified |
| Historical D1 parser comparison | 1,200 deterministic synthetic cases: 832 accepted and 368 rejected identically |

The original D3-B full run found five obsolete schema assertions (trigger inventory,
FK deletion action and three literal migration heads). Those expectations were
corrected to match the declared schema without removing checks; the complete
542-test rerun passed. D3-B.5 added ten targeted tests and the downgrade-lock
correction; its complete 552-test rerun passed. D1 tests and both native engines remain unchanged.
Research execution used verified existing Release binaries; application C++ tests
were freshly compiled. Local Linux/WSL is unavailable; no sanitizer run is claimed.

Both workflows passed actionlint 1.7.7 syntax/expression validation; 14 inline-gate
policy checks verified rejection of missing PostgreSQL, empty/incomplete discovery,
failed tests and unexpected skips. The explicit 51-test preference gate permits
no skips. The full Linux gate allows only the named Windows-only runner test;
database/tooling skips are errors. Existing research Release and ASan/UBSan jobs
remain configured. Hosted CI is unexecuted until publication; Python persistence
tests are not sanitizer coverage. No deployment steps were added.
Existing I3c synthetic-only admission and default-disabled execution are untouched.
Numerical governance, real-calendar execution, UI and D3-C/D4 remain out of scope.
