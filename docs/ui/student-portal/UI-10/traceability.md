# Student control and backend traceability

This is the UI-10 source-contract audit of the implementation based on `998d54d`, including the subsequent audit corrections. It traces control **types**, including conditionally rendered and JavaScript-created controls; repeated records, dates and options use the same contract. The generated [source control inventory](source-controls.csv) supplies template/line/attribute details. The real-browser `controls.json`, `destinations.json`, `post-states.json` and `persistence.json` files supply execution evidence for the states actually exercised. Source inspection does not imply that every possible data permutation was exercised in a browser. Read test outcomes and remaining gaps in the acceptance report.

`V` means the destination/behavior and its server contract were verified by source inspection. `D` means intentionally disabled under the stated condition. `F` means unsupported/deferred and not offered as a working control. Runtime success must additionally be supported by the recorded current test/browser results. All authenticated identities come from `g.principal`; no submitted actor/user identifier replaces the session identity. All POST forms carry `csrf_token`; fetch POSTs use the same field or the existing `X-CSRF-Token` header. Ordinary student error presentation preserves HTTP status, method headers and service authorization.

## Common persistence and response contracts

- `Database.transaction()` commits on successful exit and rolls back exceptions. Appointment, room, equipment, queue and feedback events and recipient `notification` rows are written in the same mutation transaction through `publish_event`/`queue_event`. Notifications do not determine scheduling state.
- `AppointmentService.evaluate` calls `EngineGateway.execute_appointment`; room recommendation/confirmation calls `execute_room` or `execute_room_series`; equipment matching calls `execute_equipment` or `execute_equipment_series`. The existing versioned JSON gateway validates correlation and engine results. The unchanged C++ executable supplies matching decisions; Python services retain identity, locks, revisions, persistence and permissions. Read-only calendar/dashboard/notification rendering does not run an allocation engine.
- `ApplicationState.calendar_revision`, database locks, exclusion constraints and service revalidation protect mutation snapshots. A displayed recommendation is not a reservation. Pending appointments/rooms/equipment and waiting preapproval do not create confirmed reservations.
- Current faculty/custodian responsibility is determined by the existing active account grants and service checks, not inferred from a client-supplied role label. References to student restrictions below mean ordinary students without the corresponding existing authority; no new grant or role policy is introduced.
- Mutation routes generally return **302 to the actual detail route**, then render a fresh authorized service read. Recommendations return JSON for appointments/rooms and server-rendered HTML for equipment. Service validation failures remain 409 for service forms (calendar query failures 400); denied service access remains 403; CSRF failures remain 400. Gateway/persistence availability failures use the existing 503 handlers. No client success notice is substituted for a failed operation.
